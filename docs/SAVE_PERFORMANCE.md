# セーブ・週送りの負荷改善

## 第1段階：全体保存を維持する改善

2026-10-04に実装。セーブJSONの形式、全個体・血統・戦績・リプレイの保持、進行ルールは維持する。

- 起動時には自動保存だけを取得し、5つの手動スロット本体を先読みしない。
- スロット一覧は専用の概要ストアから表示する。日時、週、所持金、所有羽数を保存する。
- 本体と概要は同じIndexedDBトランザクションで保存し、どちらかが失敗した場合は両方を巻き戻す。
- 旧スロットの概要は初回表示時に補う。本体は書き換えず、他タブで変更された場合は概要の書き込みを拒否する。
- 概要が壊れていても本体を検証して復旧できる。概要の補完に失敗しても本体のロードは可能。
- ロード操作では本体を読み直し、完全な検証と既存の競合チェックを行う。
- 保存変換は1回の呼び出し内だけで、同じレースの出走一覧・リプレイのJSON化を共有する。内容が等しい別オブジェクトの重複除去も維持する。
- 個体IDの検索索引は1回の同期的な週送り・レース確定内だけで使用し、終了時や例外発生時に破棄する。個体の追加と年末の配列置き換えに追従する。
- 今週の確定済みレースを一度の走査で調べ、レースごとの過去戦績の再走査を減らす。

差分保存や、週をまたいで保持する個体・遺伝子のキャッシュは導入していない。毎回の全体保存を維持し、変更検知フラグに依存しない。

IndexedDBのバージョンを1から2へ更新し、既存の本体ストアを残して概要ストアを追加する。旧接続は既存のversionchange処理で閉じられる。

### 試験データでの計測

6年間進行、1,354羽、セーブ本体5,198,696バイト。最適化前の変換との出力は完全一致。

| 処理 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 進行中の状態の保存変換（中央値） | 108ms | 90ms |
| ロード直後の状態の保存変換（中央値） | 102ms | 98ms |
| 5スロットの取得・展開・検証／概要取得（3回平均） | 521ms | 0.59ms |

Node.jsとfake-indexeddbでの計測。保存変換は各7回のうち最初の2回を除いた5回の中央値。スロット一覧は約29MBのスナップショット取得から計405バイトの概要取得になった。ブラウザの描画・実際のディスクI/Oは含まない。旧形式から展開した出走一覧は別オブジェクトなので、ロード直後の保存変換の改善は限定的。

## 回帰検証

- 全体テスト：`npm test`
- 保存・ロード・UI：`node tools/run-tests.cjs tests/ranch-storage.test.cjs tests/ranch-resume.test.cjs tests/ranch-ui.test.cjs`
- 保存と検索の等価性：`node tools/run-tests.cjs tests/save-performance.test.cjs`
- 長期進行：`npm run test:long`

`save-performance.test.cjs`には最適化前の保存変換を比較用に残し、保存JSONの完全一致、ロード後の往復、同じオブジェクトを編集した後の再保存を確認する。検索は線形検索との比較で、出生・年末の個体整理・NPC更新を含む状態の完全一致を確認する。

## 次の段階

1. 過去個体とリプレイの保存分割。血統表示、配合計算、称号、初勝利、過去レース観戦、バックアップの往復を保持する設計が必要。まず読み取り先の分離と移行の等価性を確認し、差分書き込みは別の変更として扱う。
2. NPCレース計算。進路選択の重複計算を減らし、固定入力で全着順・タイム・軌跡が一致することを確認する。Worker化はUI応答と状態交換の費用を測って判断する。

この段階ではセーブ本体の容量は削減していない。実ブラウザの描画・ディスクI/Oを含む体感速度は別途確認する。
